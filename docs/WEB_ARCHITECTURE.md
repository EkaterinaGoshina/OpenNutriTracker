# Архитектура веб-версии: сервер, семья, фото

Дополняет [WEB_PORT_PLAN.md](WEB_PORT_PLAN.md). План порта описывает перенос приложения в браузер, этот документ описывает серверную часть: логин, объединение пользователей в семью, общие блюда, хранение фото и хостинг.

## Исходные условия

- Приложение local-first: все данные пользователя лежат в Hive на устройстве, своего бэкенда нет.
- `supabase_flutter` подключён к проекту автора со справочником еды ([supabase-self-hosting.md](supabase-self-hosting.md)). Это не наш бэкенд. Клиент использует только `sp_food_data_source.dart`.
- Главная сущность для семьи — блюдо из «Кухни» (`RecipeEntity`). Блюдо каждый раз собирается заново, логируется граммами или порциями.
- Фото уже сжимаются в WebP q80, 1024 px по короткой стороне (`user_image_storage.dart`). Хранятся файлом, в блюде лежит относительный путь `imagePath`.

## Схема

```
Браузер (Flutter Web)
   │  один домен: app.example.com
   ├── /*        → Worker: статика Flutter-сборки (static assets)
   ├── /api/*    → тот же Worker: подпись URL для R2, AI-прокси
   │                    │
   │                    ├── R2        (фото)
   │                    └── проверка JWT и доступа к семье → Supabase
   ├── напрямую → наш Supabase   (Auth, Postgres + RLS)
   └── напрямую → Supabase автора (справочник еды, без логина)
```

| Компонент | Роль |
|---|---|
| **Cloudflare Worker со static assets** | Один деплой отдаёт и `flutter build web`, и `/api/*`. Бесплатно, HTTPS. HTTPS нужен камере и сканеру. Pages тоже подошёл бы, но тогда два деплоя вместо одного. |
| **Наш Supabase** | Логин, семьи, общие блюда, права доступа. Собственный API не пишем. |
| **R2** | Фото. Бакет приватный. 10 ГБ бесплатно, исходящий трафик не тарифицируется. |

### Почему Supabase

Правило «видит только своя семья» записывается как SQL-политика (RLS) и проверяется самой базой. Не нужно дублировать эту логику в приложении или в самописном сервере.

Альтернатива «всё на Cloudflare» (Workers, D1, своя авторизация) работает, но логин, права и синхронизацию пришлось бы писать самим. Не выбираем.

Ограничение бесплатного плана Supabase: 500 МБ базы, проект засыпает после недели без активности. Для ежедневного семейного приложения это не проблема.

### Два клиента Supabase

`Supabase.initialize` хранит сессию и обрабатывает редирект после логина, поэтому он должен смотреть на **наш** проект. Справочник еды подключается обычным `SupabaseClient(url, key)` без авторизации. В `locator` он остаётся под типом `SupabaseClient`, поэтому `sp_food_data_source.dart` и его тесты не меняются. Наш проект поднимается, только если в `.env` заданы `ACCOUNT_SUPABASE_URL` и `ACCOUNT_SUPABASE_PUBLISHABLE_KEY`. Без них в `locator` нет `AccountRepository` и `FamilyRepository`, и приложение работает как раньше.

## Аккаунт

- **Аккаунт не обязателен.** Без логина приложение работает как сейчас, полностью локально. Логин нужен только для семьи.
- Вход: шестизначный код на email и Google. Код вместо magic link работает одинаково в браузере и в мобильных приложениях, без deep links. Google пока только в вебе: на телефоне редирект требует deep link.
- **Аккаунт привязан к устройству, а не к локальному профилю.** На одном устройстве может быть несколько профилей, и у каждого свой дневник (`HiveDBProvider.perProfileBoxNames`). А блюда «Кухни» (`recipeBox`) общие для всех профилей устройства. Семья синхронизирует именно блюда, поэтому аккаунт — свойство устройства. Отдельная привязка вроде `boundUserId` не нужна: дневники разных людей и так разделены профилями.
- Выход из аккаунта стирает с устройства только блюда, полученные от семьи. Личные блюда и дневники остаются. Поэтому вход под другим аккаунтом не смешивает блюда двух семей.

## Модель семьи

```
profiles        user_id (= auth.users.id), display_name
families        id, name, created_by, created_at
family_members  family_id, user_id (unique), role (owner | member), joined_at
family_invites  code, family_id, created_by, expires_at, used_by, used_at
```

- Один человек состоит в одной семье: `unique(user_id)` в `family_members`.
- `is_family_member(family_id)` (security definer) используется во всех политиках RLS.
- Все изменения состава семьи идут через RPC: `create_family`, `create_invite`, `join_family(code)`, `leave_family`, `remove_member`, `transfer_ownership`. Прямой `insert` в эти таблицы политиками запрещён.

### Вход в семью

1. Владелец нажимает «Пригласить» и получает ссылку `app.example.com/?join=K7QM2XPA`. Код из 8 символов без похожих букв, одноразовый, живёт 48 часов.
2. Приложение при старте читает `join` из адреса и запоминает его. Параметр запроса не зависит от роутера Flutter (сейчас hash-режим) и переживает редирект логина.
3. После логина вызывается `join_family(code)`. Функция проверяет код и срок, добавляет участника и гасит код. Если человек уже в другой семье, функция возвращает ошибку, и приложение предлагает сначала выйти.

Код вместо приглашения по email: не нужна почтовая инфраструктура, ссылку можно отправить в мессенджер.

### Выход и удаление

- Участник выходит сам или его удаляет владелец. Он теряет доступ к блюдам семьи.
- Записи дневника не ломаются: `IntakeDBO` уже хранит копию блюда (`MealDBO` с нутриентами), а не ссылку на него.
- Владелец не может выйти, пока в семье есть другие участники: сначала передаёт роль. Последний участник выходит, и семья удаляется вместе с блюдами и фото.

## Общие блюда

Схема и RPC готовы ([миграция](../supabase/migrations/20261106130000_family_dishes.sql)). Экран и синхронизация в приложении — отдельная задача.

```
family_dishes   family_id, id (uuid блюда из приложения), created_by,
                payload jsonb (RecipeDBO.toJson без imagePath),
                photo_key, version, created_at, updated_at, deleted_at
                ключ: (family_id, id)
```

- Блюдо хранится одной строкой, ингредиенты лежат внутри `payload`. У `RecipeDBO` и `RecipeIngredientDBO` уже есть `toJson`. Отдельные таблицы ингредиентов не нужны.
- Ключ включает семью. Одно и то же личное блюдо можно отправить в новую семью после выхода из прошлой, строки не столкнутся.
- **Конфликты по версии, а не по времени.** Клиент сохраняет через `save_family_dish(id, payload, photo_key, base_version)` и передаёт версию, которую видел. Если кто-то успел сохранить раньше, база отвечает `dish_conflict`, и клиент показывает свежую версию вместо того, чтобы молча затереть чужую правку. Целое число переживает JSON без потерь, время с микросекундами — не всегда.
- **Удаление мягкое.** `delete_family_dish(id, base_version)` оставляет строку-надгробие: `deleted_at` стоит, `payload` пустой, `photo_key` убран. Устройство, которое было офлайн, узнаёт об удалении. Сохранить удалённое блюдо нельзя (`dish_deleted`). `base_version = null` удаляет без проверки версии. Сейчас `RecipeDataSource.deleteRecipe` удаляет из Hive насовсем — для общих блюд так нельзя.
- **Синхронизация** без Realtime: при открытии «Кухни» и по свайпу вниз запрос `updated_at > курсор`. В ответе новые, изменённые и удалённые блюда. `updated_at` ставит база. Транзакции могут закоммититься не в порядке своего `updated_at`, поэтому курсор берётся с запасом в пару минут назад. Повторно полученная строка с той же версией просто пропускается.
- Править и удалять блюдо может любой участник семьи.
- Блюдо до вступления в семью остаётся личным. После вступления новые блюда по умолчанию общие. Существующие можно отправить в семью по одному.
- Участник, которого удалили или который вышел, теряет доступ к блюдам семьи. Его блюда остаются у семьи. Приложение при выходе стирает с устройства полученные от семьи блюда.

### Видимость дневников

«Посмотреть на семью» потребовало бы выгружать на сервер личные данные. Сейчас они на сервер не попадают совсем. Откладываем: в MVP семья видит только общие блюда и состав участников.

## Фото на R2

1. Клиент сжимает фото существующим пайплайном (WebP q80, 1024 px).
2. Клиент вызывает `POST /api/photos/upload-url` с JWT от Supabase и `family_id`. Worker проверяет подпись JWT по публичным ключам Supabase (JWKS, без секрета в Worker). Затем от имени пользователя вызывает RPC `is_family_member` и возвращает подписанный PUT на `families/{family_id}/{uuid}.webp`.
3. Клиент загружает файл напрямую в R2 и записывает ключ в `family_dishes.photo_key`.
4. Чтение через `POST /api/photos/download-url`: та же проверка, подписанный GET на час.
5. Cron Trigger раз в неделю удаляет из R2 ключи, на которые не ссылается ни одно блюдо.

В блюде два поля: `imagePath` для локального файла (как сейчас) и `photo_key` для R2. В вебе файловой системы нет, поэтому локальная копия фото там хранится байтами в Hive.

Отдельная таблица `photos` в MVP не нужна. Если понадобятся квоты на семью, добавим.

## Принятые решения

| Вопрос | Решение |
|---|---|
| Хостинг | Один Worker: статика и `/api/*` |
| Бэкенд | Supabase, не «всё на Cloudflare» |
| Проекты Supabase | Два. `Supabase.instance` — наш, справочник еды — отдельный клиент |
| Обязателен ли аккаунт | Нет, только для семьи |
| Аккаунтов на устройство | Один, блюда семьи стираются при выходе |
| Семей на человека | Одна |
| Что общее | Только блюда «Кухни». Дневник остаётся личным и локальным |
| Синхронизация | По запросу, курсор по `updated_at` от сервера, конфликты по `version`, мягкое удаление |
| Ссылка-приглашение | `?join=CODE`, не путь в роутере |
